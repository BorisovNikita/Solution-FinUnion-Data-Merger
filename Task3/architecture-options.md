# Сравнение архитектурных вариантов

|Критерий|DWH на PostgreSQL|Data Lakehouse|Data Mesh|
|-|-|-|-|
|**Плюсы**|Простота, ACID, зрелость технологий, высокая скорость для структурированных данных.|Поддержка любых форматов (сырые, полуструктурированные), масштабируемость, ACID через Iceberg, дешевое хранение.|Децентрализация, доменная экспертиза, масштабируемость за счет команд, гибкость.|
|**Минусы**|Дорогое масштабирование, плохо подходит для неструктурированных данных и ML.|Сложность настройки, требует компетенций (Spark, Iceberg, Trino), возможные задержки для BI.|Высокие организационные издержки, сложность управления, требуется зрелая Data Culture.|
|**Когда подходит**|Регламентированная отчетность, классические BI-нагрузки, небольшие/средние объемы.|Большие данные, ML, исторические архивы, потоковые события, разнородные данные.|Крупные организации с множеством доменов, где централизация тормозит развитие.|
|**Применимость к FinUnion + RetailBank**|**Высокая** для промежуточного состояния (3 мес.) и регуляторной отчетности.|**Высокая** для целевого состояния: исторические данные, антифрод, ML.|**Средняя**. Полноценный Data Mesh избыточен, но элементы (Data Products) полезны.|

## Выбранный подход: Гибридная архитектура (DWH + Data Lakehouse + элементы Data Mesh)

**Обоснование выбора:**

1. **Промежуточное состояние (3 месяца):** Используем **DWH на PostgreSQL**. Это позволяет быстро собрать единую управленческую и регуляторную отчетность из двух legacy-систем без остановки сервисов. PostgreSQL обеспечивает ACID и знаком команде.
2. **Целевое состояние (12 месяцев):** Переходим к **Data Lakehouse**. Объемы исторических данных (транзакции, логи, архивы) растут, и хранить их в реляционной БД дорого. Lakehouse (Iceberg + Trino) позволяет хранить сырые данные дешево и одновременно поддерживать ACID-транзакции.
3. **Элементы Data Mesh:** Внедряем доменные **Data Products** (см. `data-products.md`) для клиентских данных, транзакций и кредитных рисков. Это позволяет бизнес-доменам (CRM, Риски, Финансы) самостоятельно владеть и управлять своими наборами данных, не создавая при этом избыточную бюрократию полноценного Data Mesh.
